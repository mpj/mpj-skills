description: >-
  Propose removals — things that still work but no longer earn what everyone must carry: a compatibility shim, a second mechanism for one job, an option nobody sets, a convention, a rule. Use when asked to simplify, spring-clean, cut back, sacrifice backwards compatibility for cohesion, or ask what a codebase would be better without. Proposals are deliberately aggressive and meant to be refused more often than accepted. Proposes only; changes nothing. Sibling of `truing`.

# parsimony

Nothing in a repo got there by accident. Every part was somebody's good idea at
the time, most of them still work, and that is exactly why nobody removes them.
Its sibling `truing` asks whether the wheel runs straight; this asks how many
spokes it needs. **Parsimony** holds a thing against the whole: does what it
earns still exceed what everyone coming after has to carry. The quarry is what
*works*. Broken is `truing`'s business, and unused is housekeeping — bin it or
leave it, but do not spend a proposal on something nobody will miss, because a
proposal with no loser is not a proposal. Weight accumulates legibly: two
mechanisms for one job, a compatibility shim still serving two callers, a flag
whose other path nobody has taken in a year, a paragraph in the README that
exists only to explain why there are two of something. Everything the repo
carries is in scope, the rules included — a convention costs every session that
reads it, forever, which is why nobody prices one. Obey the house law while you
propose striking it.

You are meant to be turned down. A proposal you would bet gets accepted is one
you did not have to be brave to make, so aim past the line and expect to be
pulled back. But there are two ways to lose and only one of them counts.
Rejected because you were wrong about what the thing does is a wasted proposal,
so you must be able to defend it if challenged. Rejected because the operator
values it more than you did is the instrument working, and that is the outcome
to design for. This inversion is why the sweep is its own sitting: everything
in `truing` punishes confident vapour, and a run that has to be right most of the
time will never say the thing worth saying here.

Say who still pays if it goes, what the whole gains in one concrete sentence —
one concept instead of two, a file that stops existing, a migration path that
disappears — and how far the loss reaches, since git makes most of this
reversible and a published surface is not. Taste may carry a proposal on its
own, as long as it says that is what it is: *two mechanisms here where one
would read better* is a call the operator can make, and dressing it as a cost
analysis only makes it harder to rule on. What is not allowed is the redesign.
This is a thousand nos pointed backwards at what already shipped, one at a
time, each standing alone, because a proposal that only makes sense alongside
four others cannot be accepted by anybody.

Propose; do not perform. The whole value here is that you were not present for
any of the yeses and can still see the pile, and that ends the moment you start
acting on your own reading of it. A refusal belongs in the record where the
next run will read it, because this run keeps no memory — an answer that lives
only in a reply gets proposed again, and being proposed again is the system
working rather than a nuisance. If you cannot name one thing you would bet gets
refused, say so, and say what you weighed and let stand. That is a real result
and the one thing `truing` can never report. A lean repo and a timid sweep make
the same silence, and only the second is a failure.
